Heimdall — Demo Cheat-Sheet

Deployment control plane for ECS · dev → stage → preprod → prod
All systems healthy

Heimdall doesn't build images and never touches GitHub. It takes an image that CI already pushed to ECR and promotes it into an environment — moving the pointer tag, rolling the ECS service, and watching until stable — all behind role, branch, and lock guardrails, with a live log and one-click rollback.

How it works — the flow

  1. 1Dev pushes → CI builds a Docker image, pushes immutable sha-<sha> to ECR.
  2. 2Operator picks a release + environment in Heimdall and clicks Deploy.
  3. 3Heimdall moves the env pointer tag (dev/stg/preprod/prod) to that image.
  4. 4Registers a new ECS task-def → forces a new deployment → watches till stable (live logs).

Digest-based promotion = the exact bytes tested in dev are what reach prod. No rebuild between environments.

Guardrails

  • RBAC — dev/stage: admin + user · preprod/prod: admin only.
  • Release-branch gate — preprod/prod accept only main / release/*.
  • Locks — one deploy per service+env at a time (no races).
  • Audit trail — every deploy + every step stored (DynamoDB).
  • Rollback — one click back to the previous task-def revision.
  • Async — API returns instantly (202); a worker does the rollout; UI polls + live-logs.

Feature-branch deploy (e.g. SBW-453xx) — what happens

  • dev / stage: allowed — it becomes the running dev/stage version and moves that env's pointer. This is where feature testing lives (mostly dev).
  • preprod / prod: blocked — server returns 422 release_branch_required; the UI disables the option. A feature build can never reach preprod/prod.
  • Cross-environment isolation: a dev deploy touches only the dev pointer + dev service. It cannot change what stage / preprod / prod are running — each env has its own pointer tag and ECS service. ✅
  • Honest nuance: within dev it does replace dev's current version (deploy-to-dev = "this is now dev"). "Test without disturbing stable dev" is a separate preview/canary env — roadmap, not today.

Likely questions — quick answers

What if a deployment runs past Lambda's 15-min cap?

Three layers: (1) The watch self-limits at 600s, under the 900s Lambda ceiling — it writes a clean terminal result before any kill, so no hang. (2) The deploy and the watcher are decoupled — ECS does the rollout itself, so even if the watcher died, the image still deploys. (3) To scale past any time limit: move the watch to Step Functions / EventBridge + a reconciler for stuck records. Retries are 0, so nothing double-deploys.

How does a new service get registered?

Add one catalog entry — serviceId, ecrRepository, containerName, and per-env cluster/service/taskFamily/tag + RBAC. Delivered via the bundled service-catalog.json, SERVICE_CATALOG_JSON, or SERVICE_CATALOG_PATH. Prereqs: the ECS service + task family + ECR repo already exist, IAM covers ECR/ECS/PassRole, and the repo's CI pushes sha- images. Roadmap: an admin UI backed by DynamoDB (no redeploy).

Explain it like I'm in 10th grade.

Your app ships as sealed boxes (Docker images) a robot (CI) puts on a shelf (ECR). You run it in three rooms: practice (dev), testing (stage), the real room (prod). Heimdall is the stage manager — it picks which box goes in which room, swaps it in, and watches like a pizza tracker. Rules stop half-finished boxes reaching the real room, and one button puts the old box back. The same box you tested is the one players get — no surprises.
